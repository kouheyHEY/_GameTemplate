## 1. 初期構想

### 1.1 ゲームコンセプト（v0.1.0: 2026/01/30）

#### タイトル: AI Agent Master

**基本コンセプト**  
お題に沿ったゲームをAIに作らせる育成シミュレーション。プレイヤーはAIコアに適切なモジュールを「ライン接続」して、リソースを供給することでゲームを生産する。

#### 計画していたコアメカニクス

```
[モジュール] ──ライン接続──→ [AIコア] → ゲーム生産
     │
     └── バグ発生 → プレイヤーがクリック修復
```

**特徴的な要素:**

- **ライン接続システム**: プレイヤーがドラッグ&ドロップでモジュールとAIコアを接続
- **バグ修復ミニゲーム**: モジュールがランダムにバグで停止し、プレイヤーが数回クリックして修復
- **リソースバランス管理**: ロジック、サウンド、イラストの3種類のリソースをバランスよく供給
- **AI成長システム**: 売上金でAIを強化し、生産速度を向上

### 1.2 計画していたモジュール群

#### ベースモジュール

- **ロジック・モジュール**: プログラムリソースを生成
- **サウンド・モジュール**: 音楽リソースを生成
- **イラスト・モジュール**: グラフィックリソースを生成

#### エクストラモジュール（強化系）

- **モジュールブースター**: リソース出力速度を高める
- **リソースメモリ**: リソースを一定量ストック
- **オートデバッガー**: バグを自動で解消
- **コアエンハンサー**: AIコアの処理速度を向上
- **アイデアチップ**: ゲームの面白みを追加（売上ランダム増加）

### 1.3 計画していた進行システム

#### ゲームタイプのアンロック

```
初級ゲーム（シンプルなパズル）
  ↓ 総売上 X 円 or 累計販売 Y 本
中級ゲーム（アクション、RPG）
  ↓ 総売上 XX 円 or 累計販売 YY 本
上級ゲーム（オープンワールド、大作RPG）
```

- **売上計算システム**: ゲームの評価に応じた売上金を獲得
- **評判システム**: リソースバランスが良いと高評価、バランスが悪いと低評価
- **アンロック条件表示**: 「あと10,000円で新しいゲームタイプがアンロック！」

### 1.4 初期構想の魅力ポイント

✨ **良かった点:**

- AIをテーマにした独自性
- リソース管理とラインパズルの融合
- 段階的なアンロック要素でモチベーション維持
- バグ修復ミニゲームによるインタラクティブ性

⚠️ **懸念点:**

- ライン接続UIの実装難易度が高い
- バグ修復ミニゲームがテンポを崩す可能性
- 売上計算システムが複雑すぎる
- エクストラモジュールが多すぎて把握しづらい

## 2. コアメカニクスの大転換

### 2.1 転換点: 「マッチ3パズル」への変更

開発初期に最も大きな方針転換が発生。**ライン接続システムからマッチ3パズルへの全面変更**を決断。

#### 変更の理由

| 問題点                           | マッチ3パズルでの解決                        |
| -------------------------------- | -------------------------------------------- |
| ライン接続UIの複雑さ             | タップ/クリックのシンプルな操作              |
| 接続ミスによるストレス           | パズルのルールが明確で直感的                 |
| バグ修復ミニゲームがテンポを崩す | パズルプレイ自体がミニゲームとして成立       |
| リソース管理の難しさ             | タイル消去で自動的にリソース生成（シンプル） |
| ゲームテンポが単調               | 連鎖システムで戦略性とスピード感を両立       |
| 実装難易度が高い                 | Phaser 3の標準機能で実装可能                 |

#### 新しいゲームフロー

```
[パズルエリア(左33%)]          [ゲーム生産エリア(右67%)]
┌─────────────┐              ┌──────────────┐
│ マッチ3パズル │              │ モジュール配置│
│      ↓      │              │              │
│ タイル消去  │──リソース生成→│   AIコア     │
│      ↓      │              │      ↓       │
│ 連鎖発生！  │              │  ゲーム生産  │
└─────────────┘              └──────────────┘
```

### 2.2 ゲーム名の変更

**AI Agent Master** → **Made in Match Factory**

- **理由**: マッチ3パズルが中心になったことで、「マッチ」をタイトルに反映
- **Factory**: 工場でゲームを生産するイメージを強調
- **Made in**: 「製造」という行為を前面に出す

### 2.3 画面レイアウトの確立

#### AreaLayoutManager（Singleton）の導入

```
画面分割:
- パズルエリア: 左側（640px）
- ゲーム生産エリア: 右側（560px）
- 合計: 1200px × 800px
- 境界線: 明確な分割線で視覚的に分離
```

**技術的工夫:**

- Singletonパターンで画面レイアウト情報を一元管理
- 各シーンから `getPuzzleArea()` で座標を取得
- リサイズ対応の基盤を確立

## 3. 実装した機能の変遷

### 3.1 パズルシステム

#### 初期構想 → 実装

| 初期構想               | 実装した内容                                  |
| ---------------------- | --------------------------------------------- |
| なし（ライン接続のみ） | 6×6グリッドのマッチ3パズル                    |
| -                      | State Patternによる厳格な状態管理             |
| -                      | 連鎖システム（倍率: 配列定義で序盤重視）      |
| -                      | スコアシステム（連鎖 + 同時消し種類ボーナス） |
| -                      | 手数制限（ノルマごとに設定、基本20手）        |
| -                      | 3連鎖以上で手数回復（+1手）                   |

#### 実装したパズルメカニクス

**基本ルール:**

- 6×6グリッドのマッチ3パズル
- タイルを選択 → 隣接タイルと交換
- 縦or横に3つ以上揃うと消去
- 上から落下して空白を埋める

**スコア計算:**

```
基本スコア = マッチ数 × 1
連鎖倍率 = [1, 2, 4, 8, 12, 16, 20, 28, 36, 44, 52]（配列で定義）
同時消しボーナス = (種類数-1) × 10 + (消した数-3) × 5
最終スコア = floor(基本スコア × 連鎖倍率 + 同時消しボーナス)
```

**手数回復システム:**

- 3連鎖以上: +1手（最大手数まで回復）
- 戦略的に連鎖を繋げることで手数を維持

### 3.2 特殊タイルシステム

#### 計画していたエクストラモジュール → 特殊タイルへ変更

| 初期構想                       | 実装した特殊タイル                   |
| ------------------------------ | ------------------------------------ |
| モジュールブースター（強化系） | **クロスブーストタイル**（十字消去） |
| オートデバッガー（自動修復）   | **スーパーボンバータイル**（全消し） |
| リソースメモリ（ストック）     | **バグタイル**（お邪魔）             |
| コアエンハンサー（速度向上）   | （未実装）                           |
| アイデアチップ（ランダム効果） | （未実装）                           |

#### 実装した特殊タイル

**1. クロスブーストタイル（🎯 十字消去）**

- 生成条件: 4つマッチ
- 効果: 十字方向のタイルをすべて消去
- 特殊効果: 場のすべてのバグタイルも同時消去
- リソース生成: 消去したタイル数に応じて計算（連鎖倍率適用）

**2. スーパーボンバータイル（💣 全消し）**

- 生成条件: 5つ以上マッチ
- 効果: スワップしたタイルと同じ種類のタイルをすべて消去
- リソース生成: 消去したタイル数に応じて計算（連鎖倍率適用）

**3. バグタイル（🐛 お邪魔）**

- 生成条件: 落下時にランダム生成（5%）
- 効果: なし
- リソース: なし（邪魔するだけ）
- 消去方法: 特殊タイルの効果範囲に含める

**チュートリアル対応:**

- 各特殊タイル初生成時に専用チュートリアルを表示
- スポットライト機能で該当タイルのみ操作可能に
- 状態管理で2回目以降は表示しない

### 3.3 ゲーム進行システム

#### 初期構想 → 実装

| 初期構想                              | 実装した内容                               |
| ------------------------------------- | ------------------------------------------ |
| 売上金によるアンロックシステム        | ノルマクリアによる進行システム             |
| 総売上 or 累計販売本数                | 指定ゲームを指定数生産                     |
| 3段階のゲームタイプ（初級/中級/上級） | 6種類のゲームタイプ（段階的アンロック）    |
| 評判システム（リソースバランス）      | スコアシステム                             |
| 売上による進捗表示                    | ノルマ進捗表示（例: 5/10）                 |
| -                                     | 固定ノルマ7つ + 無限モード（パッケージ版） |

#### ノルマシステムの詳細

**ノルマ構成:**

```typescript
{
  gameTypeId: "rpg",        // 対象ゲームタイプ
  productionQuota: 4,       // 必要生産数
  maxMoves: 20,             // 手数制限
  description: "RPGゲームを4本作成",
}
```

**固定ノルマリスト（7つ）:**

1. パズルゲーム 5本（20手）
2. ビジュアルノベル 5本（20手）
3. リズムゲーム 5本（20手）
4. パズルゲーム 10本（20手）
5. アクションゲーム 5本（20手）← **体験版はここまで**
6. アドベンチャーゲーム 4本（20手）
7. RPG 4本（20手）

**進行フロー:**

1. ノルマ表示: 「RPG を 4個 生産してください」
2. パズルでリソース集め（最大20手）
3. AIコアがゲーム生産（自動）
4. ノルマ達成 → 次のノルマへ
5. 5つ目のノルマクリアで体験版終了

**体験版制限:**

- デモ版: 5つのノルマまでプレイ可能
- ノルマクリア後に購入促進シーン表示
- パッケージ版: 固定7つ終了後も無限モード（ランダムノルマ）で継続プレイ可能

## 4. 技術的な挑戦と学び

### 4.1 アーキテクチャ設計

#### 適用したデザインパターン

| パターン      | 適用箇所                          | 効果                                |
| ------------- | --------------------------------- | ----------------------------------- |
| **Singleton** | AreaLayoutManager, VersionManager | 画面情報とバージョン情報の一元管理  |
| **State**     | PuzzleState, TutorialState        | 状態遷移の厳格な管理                |
| **Observer**  | イベント駆動通信                  | パズル⇔ゲーム生産エリアの疎結合連携 |
| **Factory**   | PuzzleTileFactory                 | タイル生成ロジックの集約            |
| **Manager**   | 各種マネージャークラス            | Sceneの軽量化                       |

#### Scene の軽量化戦略

```typescript
GameScene の責務:
✅ ライフサイクル管理（create, update, shutdown）
✅ マネージャーの初期化
✅ イベントのルーティング

❌ 複雑なゲームロジック → PuzzleManager へ
❌ UI表示ロジック → QuotaDisplay へ
❌ サウンド管理 → SoundManager へ
```

**効果:**

- GameScene.ts が約1700行だが、責務は明確
- テストしやすい構造
- 機能追加時に影響範囲が限定的

### 4.2 イベント駆動アーキテクチャ

#### 実装したイベント通信

```typescript
// パズル → ゲーム生産エリア
this.scene.events.emit("puzzle:match", {
    moduleType: "game",
    count: 3,
    chainCount: 2,
    multiplier: 1.2,
    resourceCount: 6, // ボーナス込み
});

// AIコア → UI
this.scene.events.emit("game:completed", gameTypeId);

// UI → ゲームロジック
this.scene.events.on("quota:cleared", (data) => {
    // 次のノルマへ
});
```

**利点:**

- クラス間の疎結合
- 機能追加・削除が容易
- イベント名を定数化で typo 防止

### 5.1 削除した機能（初期構想から）

#### ライン接続システム

**理由:** マッチ3パズルに変更したため不要に

#### バグ修復ミニゲーム

**理由:** パズルプレイ自体がゲーム性を持つため、テンポを崩す要素として削除

#### 売上・評判システム

**理由:** ノルマシステムに変更したため不要に

#### リソースメモリ

**理由:** パズルからの即時リソース生成に変更したため、ストックの必要性がなくなった

#### オートデバッガー

**理由:** バグ修復ミニゲームを削除したため不要に

**理由:** ゲーム生産速度は固定に変更

#### アイデアチップ（ランダム要素）

**理由:** スコアシステムに変更したため不要に

### 5.2 未実装の機能（時間・優先度の都合）

#### モジュール配置のカスタマイズ

- **構想:** プレイヤーがモジュール配置を変更可能
- **現状:** 固定配置（初期モジュール3つのみ）
- **理由:** パズル要素を優先したため、簡略化

#### ゲームタイプのアンロック

- **構想:** 段階的にゲームタイプ解放
- **現状:** 6種類のゲームタイプが段階的にアンロック（総売上・累計販売本数で解放）
- **実装:** 初期は「パズルゲーム」のみ。ロジック単体 → ロジック+単一リソース → 全リソースバランス型へと段階的に開放

#### セーブ/ロード機能

- **構想:** ゲーム進行状態の永続化
- **現状:** チュートリアル状態のみ永続化
- **理由:** 体験版は短時間でクリア想定のため優先度低

#### BGM/SE音量調整

- **構想:** オプション画面で音量変更
- **現状:** 固定音量（BGM: 0.8, SE: 1.0）
- **理由:** 実装時間の都合

#### マルチプラットフォーム対応

- **構想:** スマホ版リリース
- **現状:** PC版のみ（ブラウザ + Electron）
- **理由:** 開発期間の制約
